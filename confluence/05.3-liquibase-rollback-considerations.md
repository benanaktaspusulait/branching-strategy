## Summary

This page covers Liquibase-specific rollback rules, expand/migrate/contract patterns and release readiness requirements for database changes.

---

## Current Understanding

- Liquibase is used for database schema and data changes.
- One Liquibase update may affect multiple projects.
- Liquibase changesets are typically applied once and tracked by checksum.
- There is no standard rollback block requirement documented.

---

## Rollback Rules By Scenario

| Scenario | Action |
|----------|--------|
| Schema change with rollback block | Execute Liquibase rollback as part of release rollback. |
| Schema change without rollback block | Fix-forward only. Document why rollback not possible. |
| Destructive data change (DROP, DELETE) | Cannot roll back. Fix-forward or restore from backup. |
| Additive-only change (ADD COLUMN, new table) | May not need rollback if application handles both states. |

---

## Expand / Migrate / Contract Pattern

For complex schema changes, the safer pattern is:

1. **Expand** — Add the new column/table/index without removing anything. Application code handles both old and new schemas.
2. **Migrate** — Move data from old structure to new. Application code uses new structure.
3. **Contract** — Remove old columns/tables only after confirming all services use new structure and at least one release has passed successfully.

This pattern makes each step independently rollbackable:
- Expand can be rolled back by removing the new column (it is unused).
- Migrate can be rolled back by repointing to the old column (data still exists).
- Contract is the only irreversible step, and it happens last.

---

## Suggested Practice

```text
Every production Liquibase changeset should include a rollback block or a documented justification for why rollback is not supported.
```

---

## Release Readiness For Liquibase Changes

Release readiness for changes that include Liquibase should confirm:

1. Rollback block exists, or explicit documentation explains why not.
2. The change has been tested in a lower environment with the same rollback path.
3. The team understands whether fix-forward or rollback is the plan if the release fails.
4. If rollback is not possible, this is flagged in the release report.
5. Non-rollbackable changes are called out during release readiness review.

---

## Risk

Database changes are often the reason a release cannot be rolled back. If the application has already written data in a new format, reverting the schema can cause data loss or corruption. This is why the expand/migrate/contract pattern and explicit rollback-block requirements are important.
